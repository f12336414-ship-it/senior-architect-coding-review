# 先复用，再决定结构

用于设计、编码和简单性审查。目标是减少完成当前需求所需的概念与变更扩散，不是把所有项目改成同一种架构。

## 1. 先查能力，后写实现

沿任务的实际调用链检查：

1. 项目已有实现、公共函数、约定、配置与测试。
2. 当前版本的框架、标准库、官方 SDK 及其扩展点。
3. 前两项有实际缺口时，再评估维护活跃、兼容、许可证合适且足够轻的现成组件。
4. 仍无法满足已确认需求时，只自研缺失部分。

判断可复用不能只看 API 名称相似。核对取消、错误、生命周期、事务、权限、幂等、数据格式与兼容语义；用代码、当前版本文档或最小探针验证。版本或行为无法核实就标记未知，不编造能力，也不自动下载或引入依赖。

小任务一句话说明复用位置和验证即可。正式设计记录候选能力、证据位置、满足项、具体缺口和选择理由。没有检查过不等于不存在；不要为获得“统一风格”重写已有设施或包一层等价 API。

新增依赖仍受执行权限约束；若现有能力存在会破坏业务或安全语义的缺口，不得为了复用而删除必要控制。

## 2. 按变化与约束选结构

先回答：哪些行为一起变化？哪条规则需要唯一权威位置？当前有什么复杂度值得隐藏？

| 当前证据 | 可考虑的最小结构 | 不应自动附带 |
| --- | --- | --- |
| 既有项目的局部功能 | 沿现有所有者和约定最小修改 | 全项目搬迁、风格统一、重写旧架构 |
| 简单 CRUD、规则少且入口局部 | 框架原生 handler、事务脚本或局部功能模块 | 空 Domain、透传 Service、通用 Repository/UnitOfWork |
| 同一功能反复横跨技术目录、共同变化 | 按功能聚合相关代码或深化现有模块 | 所有项目强制 vertical slice |
| 多个调用方共享复杂规则或状态不变量 | 封装规则的领域模块、状态模型或明确业务边界 | 每张表一个实体/仓储/服务 |
| 外部协议变化、权限/资源隔离或困难测试边界 | 能封装实际差异的薄适配器或端口 | 给每个函数/SDK/ORM 建接口和包装层 |

分层、DDD、Clean/Hexagonal、模块化单体都可以有价值，但必须服务于当前约束。高风险要求更多证据与复核，不意味着更多层。用户明确要求某种结构时遵守范围，同时说明其具体成本；不要借优化擅自替换既有架构。

框架类型可以出现在局部请求处理、框架扩展点和数据访问中。只有它们污染真实的核心策略、跨边界契约或妨碍必要验证时，才引入转换与隔离。

## 3. 新抽象的删除测试

对本次新增的层、接口、服务或包装器问：

- 删除后直接调用已有能力，权限、事务、错误、生命周期、业务语义和必要测试是否仍等价？如果是，这层可能只是透传。
- 删除后复杂度是否泄漏到多个调用方，或失去不变量、协议转换、隔离和资源所有权？如果是，保留能隐藏这部分复杂度的最小边界。
- 当前调用方能否只理解小而完整的接口，而不必反复穿越多层才能完成一个行为？

第二个真实实现、重复知识分叉或核心策略/外部边界可以支持抽象；不必等到两个实现才保护安全或事务边界。也不要仅凭目录名称、类数量、代码行数或“只有一个实现”判定过度设计。

删除测试是反事实审查，不是授权删除文件。结构调整后检查旧调用、配置、依赖和文档；仅清理授权范围内已无用途的路径，不保留两套等价实现。

## 4. 反方必须检验的两个方向

- **过度设计**：已有能力是否已满足需求？新层隐藏了什么真实复杂度？是否存在语义等价、成本更小的方案？
- **过度简化**：减少层次是否丢失权限、事务、核心规则、兼容性、取消或故障隔离？复用的能力是否真的支持所需语义？

每项质疑都回到可达场景、代码位置和行为证据。先验证发现，再要求修改；没有新增层不是失败，出现 Domain 也不是失败。
